# JARVIS Frontend → Backend Integration Specification

> **Generated by analyzing the frontend in this repository.**
> **Do not modify frontend files. This document describes what the backend must implement.**

---

## 1. Current Frontend Architecture

- **Framework**: React 19 + TypeScript + Vite
- **State Management**: React Context (`JarvisProvider` + `useJarvis` hook)
- **Styling**: Tailwind CSS v4 + Framer Motion
- **Build**: Vite with custom telemetry plugin

## 2. State Machine (JarvisStatus)

Defined in `src/store/types.ts`:

```typescript
type JarvisStatus = 'idle' | 'thinking' | 'speaking' | 'offline'
```

### Current State Transitions (Frontend-Driven)

| From | To | Trigger |
|------|-----|---------|
| `idle` | `thinking` | User sends message via `CommandConsole` OR clicks QuickNav mode button |
| `thinking` | `idle` | Mock response received (after 1.2-2s timeout) |
| `idle` | `speaking` | Not yet implemented (AudioSynth visualizes this state) |
| Any | `offline` | Not yet implemented |

### Components Consuming Status

- **CommandConsole** - Disables input when `thinking`, shows "J.A.R.V.I.S is thinking..." placeholder
- **AudioSynth** - Renders different waveform amplitudes per state:
  - `thinking`: amplitude 20, frequency 0.09
  - `speaking`: amplitude 14, frequency 0.05
  - `idle`: amplitude 7, frequency 0.05
- **QuickNav** - Sets `thinking` for 2s on mode button click

## 3. Message Format (Chat Interface)

### Frontend → Backend (via `sendMessage(prompt: string)`)

Currently: Direct function call in React context.
**Expected**: WebSocket/IPC message to backend.

```typescript
// Current mock in JarvisProvider.tsx
const sendMessage = async (prompt: string) => {
  setStatus('thinking')
  setMessages((m) => [...m, { id: Date.now().toString(), role: 'user', content: prompt, timestamp: Date.now() }])

  await new Promise((r) => setTimeout(r, 1200 + Math.random() * 800))
  const reply = 'Acknowledged. Executing directive: "' + prompt + '".\n\nThis is a frontend-only mock response...'
  setMessages((m) => [...m, { id: (Date.now() + 1).toString(), role: 'assistant', content: reply, timestamp: Date.now() }])
  setStatus('idle')
}
```

### Message Schema (Frontend `ChatMessage`)

```typescript
interface ChatMessage {
  id: string           // Currently timestamp string
  role: 'user' | 'assistant'
  content: string      // Markdown-supported (whitespace-pre-wrap rendered)
  timestamp: number    // Date.now()
}
```

### Expected Backend Response Format

```json
{
  "type": "chat_response",
  "message": {
    "id": "unique-id",
    "role": "assistant",
    "content": "Response text with markdown support",
    "timestamp": 1234567890
  },
  "status": "idle" | "speaking"  // Next state for frontend
}
```

### Tool Call Flow (Not Yet Implemented)

Frontend expects tool calls to be handled by backend. When LLM wants to call a tool:

```json
{
  "type": "tool_call",
  "tool": "tool_name",
  "params": { ... },
  "call_id": "unique-call-id"
}
```

Backend executes tool, then returns:

```json
{
  "type": "tool_result",
  "call_id": "unique-call-id",
  "result": "tool output",
  "error": null | "error message"
}
```

Then LLM continues and sends final `chat_response`.

## 4. Telemetry API

### Current: Vite Dev Server Plugin (`/api/telemetry`)

**GET `/api/telemetry`** → Returns:
```json
{ "cpu": 24, "ram": 48, "gpu": 12 }
```

### Frontend Polling

- **Component**: `TelemetryUpdater` in `App.tsx`
- **Interval**: Every 2 seconds
- **Consumer**: `SystemHealth` component displays CPU/RAM/GPU bars + uptime

### Backend Must Provide

- Same endpoint `/api/telemetry` (HTTP or WebSocket push)
- Same JSON shape
- Real system metrics (not simulated)
- Uptime tracking (frontend computes its own from session start)

## 7. Required Backend Endpoints / WebSocket Events

### HTTP Endpoints (Minimum)

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/telemetry` | System metrics (CPU, RAM, GPU %) |
| GET | `/api/health` | Backend health check |
| POST | `/api/mic` | Global-hotkey hook: broadcasts `mic:toggle` to all connected UIs |
| POST | `/api/chat` | Send message, get response (if not WebSocket) |

### WebSocket Events (Preferred for Real-Time)

#### Frontend → Backend

| Event | Payload | Description |
|-------|---------|-------------|
| `chat:message` | `{ prompt: string, message_id: string }` | User sends message |
| `audio:input` | `{ audio: string (base64), mime: string, message_id: string }` | Mic utterance for STT -> chat flow |
| `tool:confirm` | `{ call_id: string, confirmed: boolean }` | User confirms destructive action |
| `system:command` | `{ action: string, params: object }` | Direct system command (future) |

#### Backend → Frontend

| Event | Payload | Description |
|-------|---------|-------------|
| `chat:response` | `{ message: ChatMessage, status: JarvisStatus }` | LLM response |
| `chat:transcript` | `{ message: ChatMessage (role user) }` | Mic speech transcribed by backend STT |
| `audio:play` | `{ message_id: string, audio: string (base64 MP3), mime: string }` | Spoken reply for frontend playback |
| `mic:toggle` | `{}` | Toggle mic recording (from POST /api/mic); provider forwards as `jarvis:mic-toggle` window event |
| `chat:stream` | `{ delta: string, message_id: string }` | Streaming tokens (optional) |
| `tool:call` | `{ call_id: string, tool: string, params: object, description: string }` | Request confirmation for destructive tool |
| `tool:result` | `{ call_id: string, result: string, error?: string }` | Tool execution result |
| `status:change` | `{ status: JarvisStatus }` | Explicit state change |
| `telemetry:update` | `{ cpu: number, ram: number, gpu: number }` | Push telemetry (replaces polling) |
| `notification` | `{ title: string, message: string, level: 'info'|'warning'|'error' }` | Toast notification |

## 9. Permission / Confirmation Flow (Frontend Requirements)

Per architecture: **Destructive tools require explicit confirmation**.

### Frontend Needs

1. **Receive** `tool:call` event with `description` explaining what will happen
2. **Show** confirmation modal/dialog with:
   - Tool name
   - Description (e.g., "About to delete `~/Downloads/old.zip`. Confirm?")
   - Confirm / Cancel buttons
3. **Send** `tool:confirm` with `confirmed: true/false`
4. **Receive** `tool:result` with success/failure
5. **Re-verification**: Backend must verify action succeeded before reporting success

## 10. Audio / Voice Synthesis

### Persona

JARVIS speaks as the Iron Man AI (system prompt in `bridge/server.py`):
formal British butler, dry wit, addresses the operator ONLY as "sir".

### Implemented (voice loop is live)

- **Out**: backend synthesizes every reply (Edge-TTS `VOICE_ID`, capped at
  `VOICE_REPLY_MAX_CHARS`) and pushes `audio:play` (base64 MP3). Frontend plays
  it via `<audio>`, sets status `speaking` for the duration (AudioSynth
  visualizes it), then returns to `idle`. TTS failure never blocks the text.
- **In**: mic button in `CommandConsole` records (MediaRecorder webm/opus) and
  sends `audio:input`. Backend transcribes with local faster-whisper
  (`STT_MODEL`), echoes `chat:transcript` as the user bubble, then runs the
  normal chat flow. Toggle with `VOICE_ENABLED` in `backend/.env`.
- Note: mic requires a secure context — works on `localhost`, needs HTTPS otherwise.

## 11. Development vs Production

### Development (Current)

- Vite dev server serves frontend on `http://localhost:5173`
- Vite plugin serves `/api/telemetry`
- Backend runs separately (WebSocket on different port, e.g., `ws://localhost:8765`)

### Production

- Frontend built to `dist/` (static files)
- Backend serves static files + API + WebSocket on same port
- Or reverse proxy (nginx) routes `/api/*` and `/ws` to backend
